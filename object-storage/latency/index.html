버킷 이전 중 앱 요청 측정

S3 버킷을 GCS로 옮기는 동안 앱이 계속 쓰고 읽고 지울 때, 요청이 실패하지 않았는지와 지연이 얼마나 늘었는지를 실제 클라우드에서 쟀습니다.

결론

  • 이전의 모든 단계(전체 복사부터 완료까지)에서 앱의 쓰기·읽기·삭제 요청이 한 건도 실패하지 않았습니다. 성공 응답을 받은 객체는 최종 버킷에 모두 있었고, 지운 객체는 남아 있지 않았습니다.
  • 쓰기와 읽기 지연은 이전이 없을 때(같은 버킷에 직접 요청) 수준을 유지했습니다. 버킷을 바꾸는 전환 순간에도 가장 느린 쓰기가 , 가장 느린 읽기가 였습니다.
  • 삭제는 이전 중에 약 3배 느립니다(p50 기준 이전 없이 135~165ms, 이전 중 390~525ms). 지우기 전에 이전 서버에 키를 기록하고, 양쪽 버킷에서 모두 지우기 때문입니다. 이전이 끝나면 다시 이전 없을 때 수준으로 돌아옵니다.
  • 이전 서버를 kill -9로 세 번 죽였다 살린 시험에서도 실패는 0건이었습니다. 서버가 죽어 있는 몇 초 동안 쓰기와 읽기는 영향이 없었고, 삭제만 서버가 돌아올 때까지 최대 약 4초 기다렸습니다.

무엇을 어떻게 쟀나

앱 서버 3개를 흉내 내는 시험 도구(appsim)가 이전 내내 요청을 보냈습니다. 각 앱은 실제 앱이 쓸 저장소 모듈을 거쳐, 이전 서버가 알려 주는 라우트대로 버킷에 직접 요청합니다.

  • 앱마다 0.3초마다 쓰기, 0.1초마다 읽기, 쓰기 4번에 한 번 이전 객체 삭제. 세 앱을 합쳐 초당 쓰기 약 10건, 읽기 약 30건입니다.
  • 읽은 내용이 쓴 내용과 다르거나, 지운 객체가 읽히거나, 요청이 오류를 내면 실패로 셉니다. 저장소 모듈 안의 재시도를 거친 뒤 앱이 받은 결과 기준입니다.
  • 이전이 끝나면 최종 버킷을 목록으로 읽어 누락과 잔존을 확인합니다.
  • 지연은 앱이 요청을 보내 응답을 받기까지의 시간입니다. 요청마다 그 순간 앱이 쓰던 라우트의 단계를 같이 기록해 단계별로 나눴습니다.
  • 기준값은 같은 부하를 이전 없이 S3와 GCS에 직접 3분씩 보내 쟀습니다.

버킷: S3 foxtrot-om-src-test(ap-northeast-1, 객체 약 1만 개) → GCS foxtrot-om-gcs-dst-test(asia-northeast1). 서버 상태는 DynamoDB, S3 변경 감지는 SQS. appsim과 이전 서버는 한국의 개발용 Mac에서 돌았으므로 지연에는 한국→도쿄 왕복 시간이 들어 있습니다. 앱이 같은 클라우드 리전 안에서 돌면 절대값은 더 작습니다.

단계별 지연 (장애 없는 이전)

요청 건, 약 분. 단계마다 1분 이상 머물게 해서 단계별로 충분한 요청이 쌓이게 했습니다. 단위는 밀리초입니다.

전환은 두 번에 나뉩니다. ① 모든 앱이 GCS도 읽게 한 뒤 ② 쓰기를 GCS로 옮깁니다. 각 단계는 모든 앱이 새 라우트를 적용했다고 보고해야 다음으로 넘어가므로, 어떤 앱도 옛 라우트로 쓰는 동안 버킷이 바뀌지 않습니다. ①은 몇 초밖에 안 걸려 요청 수가 적습니다.

장애 없는 이전

서버 강제 종료 3회 (빨간 선)

서버를 강제 종료했을 때

같은 이전을 하면서 이전 서버를 전체 복사 중, 동기화 중, 전환과 resume 사이에 kill -9로 죽이고 약 3초 뒤 다시 띄웠습니다. 요청 건, 실패 건, 최종 버킷 누락 0·잔존 0.

  • 쓰기와 읽기는 앱이 버킷에 직접 하므로 서버가 죽어도 그대로 됩니다. 앱은 마지막으로 받은 라우트를 5초 임대 동안 계속 쓰고, 서버가 돌아오면 0.2초 간격으로 다시 받아 임대를 갱신합니다.
  • 삭제는 이전 중에는 먼저 서버에 키를 기록해야 하므로, 서버가 없는 동안 재시도하며 기다립니다. 그래서 강제 종료가 있었던 단계의 삭제 최대가 2.8~4.1초입니다. 실패로 넘어간 삭제는 없었습니다.
  • 서버가 5초 넘게 돌아오지 않으면 임대가 끝나 앱 요청이 실패하기 시작합니다. 옛 라우트로 계속 쓰다가 데이터가 갈리는 것보다 멈추는 쪽을 택한 설계입니다.

지금까지의 모든 이전 시험

같은 도구로 다른 방향들도 시험해 왔습니다. SeaweedFS는 온프렘 대용으로 개발용 Mac의 Docker에서 돌았기 때문에 그쪽 지연은 수 ms로 짧습니다.

* SeaweedFS→SeaweedFS 첫 강제 종료 시험에서 쓰기 2건이 실패했습니다. 서버가 3.3초 내려가 있는 동안 앱이 라우트 갱신에 실패한 뒤 다음 갱신까지 기다리다 임대가 끝났기 때문입니다. 갱신 실패 시 0.2초마다 다시 묻도록 고친 뒤 같은 시험을 반복해 0건이 됐고, 이후 시험은 모두 0건입니다. 누락·잔존의 “–”는 그 시험 때 appsim에 최종 버킷 대조 기능이 아직 없었다는 뜻입니다.

한계

  • 객체는 수십 바이트짜리 작은 파일입니다. 큰 객체를 쓰는 앱의 지연은 따로 재야 합니다.
  • 부하는 초당 40건 수준입니다. 실제 서비스 규모의 부하에서는 재지 않았습니다.
  • 각 측정은 한 번씩만 돌렸습니다. 클라우드 쪽 순간 지연(최대값)은 실행마다 수백 ms씩 달라질 수 있습니다.
  • 앱과 서버가 한 곳(개발용 Mac)에서 돌았습니다. 앱 여러 대가 다른 곳에 흩어진 경우는 시험하지 않았습니다.
